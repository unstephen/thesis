Back in late last year, Intel introduced a new class of CPU: hybrid CPUs that combine two different core types onto a single SoC. Intel refers to these as our P-cores, or performance cores, which each have their own L2 cache. These are designed around single- and lightly-threaded workloads where performance is critical. In addition to this we have our E-cores, built in blocks of four, with four E-cores sharing an L2 cache. This allows us to scale out the architecture for multi-threaded workloads. All the cores communicate through a shared L3 cache. The cores themselves share a common ISA, so the OS can migrate threads from one core type to another seamlessly. This does mean that the P-cores do not support AVX-512. From an OS point of view all the cores can be enumerated using CPUID or GetLogicalProcessorInformation, with the extended version of that function also providing a performance rating for the core types. One thing I'd like to mention before we move on is Intel's Thread Director. This is a piece of hardware that sits between the cores and the OS. Its job is to monitor the instruction mix it's currently running and provide hints to the OS on where best to schedule work. For example, if the Thread Director noticed a thread was very SIMD heavy, it would hint to the OS that this is best scheduled on a P-core. Likewise, if it detected a thread with a lot of user-mode waits, it would hint this is best scheduled on one of the E-cores, where it could wait in a more efficient state and free up resources on the P-cores.

去年年底，Intel 推出了一类全新的 CPU：混合架构 CPU，把两种不同的核心类型集成到单颗 SoC 上。Intel 把其中一类称为 P 核（性能核），每个 P 核有自己私有的 L2 缓存，它们围绕"性能关键的单线程与轻线程负载"设计。除此之外还有 E 核（能效核），以四个为一组构建，四个 E 核共享一个 L2 缓存，这让架构能够为多线程负载向外扩展。所有核心通过共享的 L3 缓存通信。这些核心本身共享同一套指令集（ISA），因此操作系统可以把线程从一种核心无缝迁移到另一种核心。这也意味着 P 核不支持 AVX-512。从操作系统角度看，所有核心都可以用 CPUID 或 GetLogicalProcessorInformation 枚举，后者的扩展版本还会为不同核心类型提供性能评级。在继续之前我想提一下 Intel 的 Thread Director（线程导向器）。这是一块位于核心与操作系统之间的硬件，它的职责是监控当前正在运行的指令混合情况，并向操作系统提供"在哪里调度最合适"的提示。举例来说，如果 Thread Director 发现某个线程 SIMD 指令占比很高，它就会向 OS 提示这个线程最好调度到 P 核上；同样，如果它检测到某个线程有大量用户态等待，它会提示这个线程最好放到某个 E 核上——在那里可以以更节能高效的状态等待，同时把 P 核的资源释放出来。

收尾的三句话实际上把全场的技术逻辑收束成一条链，值得作为理解 2022 年"4K 光追"商业方案的模板。第一环：CPU 侧通过 P 核绑定 + 任务图加宽，保证喂给 GPU 的 draw/compute 队列不挨饿——这一环和书架里 CoD MW 2020 强调的"CPU 提交路径是光追的第一瓶颈"完全一致，光追的加速结构管理、异步队列调度都是 CPU 密集型工作，CPU 跟不上时 GPU 会出现气泡。第二环：光追本身走"混合增量"路线（反射补 SSR、阴影精化 CSM、内容侧手工剔除），绝不做全量替换。第三环：光追推高了每像素成本，于是用 AI 上采样把内部分辨率降回 1080p，后处理留在 4K——三环各自独立成立，缺一环整个 4K 光追方案就不成立。 从书架纵向对照看演进脉络很有意思：CoD MW 2020（2019-2020）是"光追如何被塞进 60fps 引擎"的早期探索，重点在管线重叠与简化材质；Cold War 2021（2020-2021）把混合降噪与太阳阴影的分工打磨成熟；Hitman 3（2022）则代表"第三代"——光追作为 DLC 级增量、以厂商工程团队驻场的方式落地，并首次把 AI 上采样作为标配组合。三个时间点连起来，能看到实时光追从"技术验证"到"产品特性"的完整迁移路径。 留一个批判性提醒：整场演讲的所有性能数据都来自 NVIDIA RTX 3080 和 Intel 自家 CPU/GPU 组合，没有给出 AMD 显卡或 ARC 显卡上的光追数据，也没有公开 XeSS 在非 Intel 硬件（DP4a 路径）上的实测。演讲本身的立场是 Intel 的生态推广，读者应把性能结论视为"该硬件组合下的最优配置"，而不是跨厂商可迁移的通用结论——尤其是 async compute 的收益和 XeSS 的推理成本，在不同架构上差异可能相当大。
