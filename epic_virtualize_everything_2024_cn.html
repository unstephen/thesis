英文原文
Fundamentally, these features are meant to help make the most efficient use of time and memory — both time and memory on the GPU, and your time and memory as developers. But what is a "virtual"? What does virtual mean? We kind of yada-yada past this — we're like, yeah, yeah, it's virtual, look at the textures, it's fine. But it's really important to understand what it means to virtualize something in order to make the most efficient use of these features and take full advantage of them. And the easiest way I can explain this is: when we virtualize something, we create a sparse version of it — only the bits that we need — and we figure out the bits that we need based on a feedback pass. So imagine we've got, like, a book, a PDF of a book. We know how many pages are in the book, and we know what page the PDF viewer is looking at right now — page 100. So instead of sending the whole book into the GPU to be rendered or looked up, we just send the page that we need, and maybe the two pages on the other side, and we send those up to the GPU, because those are the only bits that we actually need to render, right? That's it. That's all it is. Figure out the bits that we need, send it to the GPU, leave behind the rest.

从根本上说，这些特性的目的都是帮助我们把时间和内存用得最有效率——既指 GPU 上的时间和内存，也指你作为开发者自己的时间和精力。但“虚拟”到底是什么意思？我们往往一句话带过：“对对对，它是虚拟的，你看纹理都虚拟了，没事的。”可是，要想把这几项特性用到位、吃干净，就必须真正理解“把一个东西虚拟化”意味着什么。我能给出的最简单的解释是：当我们虚拟化某个东西时，我们为它创建一个稀疏版本——只保留我们需要的那些部分——而我们是通过一个反馈通道（feedback pass）来判断“需要哪些部分”的。想象我们手上有一本书，一本 PDF 电子书。我们知道这本书有多少页，也知道阅读器当前正看在第几页——比如第 100 页。那么与其把整本书塞进 GPU 去渲染、去查找，我们只把需要的那一页、再加上摊开的另外两页送上去——因为这才是我们真正需要渲染的全部内容。就这么多，原理全在这儿：搞清楚需要哪些部分，把它们送到 GPU，剩下的留在后面。

🔍 专家解析

这是全场最重要的一页定义，值得拆成三个不可分割的构件来记。（1）稀疏化：驻留集（resident set）只是全集的一个子集，且这个子集随时间变化；（2）需求探测：必须有一个机制在每帧回答“现在需要什么”——这就是反馈通道；（3）按需供给：把需求映射到物理资源上（页表 + 上传）。任何“虚拟化”系统都缺一不可，虚拟纹理、Nanite 虚拟几何体、虚拟阴影贴图三者在这套骨架上完全同构，差别只在“需求怎么测、页有多大、错误度量是什么”。书的类比里还有一个常被忽略的细节：“再加上摊开的另外两页”——这暗含局部性假设：下一帧需要的资源与当前帧高度相关。这个假设正是所有虚拟化系统的失效根源：它依赖上一帧的反馈来供给下一帧，天然滞后一帧。所以相机快速运动、遮挡突然打开、传送/切换镜头时，会出现虚拟纹理模糊、Nanite 几何体细节不足这类“页未就绪”症状；各系统都用预取（prefetch）和驻留宽限来缓解，但无法根除。对工程实践的直接推论是：任何虚拟化特性都不能只看“静态稳态”的表现做验收，必须用最恶劣的相机路径（快速平移、贴墙、掉头）压测。另外注意他把“开发者的时间”也算进成本——后面 Convert to Virtual Texture、Render Resource Viewer、池自动增长这些 5.4 新功能，全部是在偿还这一半的成本，而不是 GPU 成本。

But why did we need to do this? Well, back in the day, we really only needed to send a few things to the GPU: textures, static meshes, skeletal meshes, maybe animations — and that's all we really needed to worry about in memory. But then, as more graphics features came online, they had to fight for the same amount of VRAM, because it turns out that the video memory that we have access to is not growing at the same rate as the stuff that we're trying to put into video memory. So now we've got features like distance fields and Lumen and Nanite and ray tracing, and all of these things, and shadows — all of these things are fighting for more or less the same amount of virtual memory, or video memory. So if we virtualize a bunch of these features, we can limit the impact of each of these features on the GPU. So the first one I want to tackle — the really big one — is textures, because those were, for the longest time, kind of the biggest offender on the GPU.

那我们为什么非得这么做？早些年，我们真正需要送上 GPU 的东西没几样：纹理、静态网格体、骨骼网格体，也许再加动画——内存层面需要操心的就这些。但随着越来越多的图形特性上线，它们都得去抢同一块显存（VRAM），因为现实是：我们所能获得的视频内存，其增长速度跟不上我们想塞进视频内存的内容的增长速度。于是现在我们有了距离场（distance field）、Lumen、Nanite、光线追踪、阴影等等这一堆特性，它们全都在争夺差不多同一份额的视频内存。所以如果我们把其中一批特性虚拟化，就能限制每一个特性对 GPU 造成的冲击。我想先啃的第一个，也是最大的一块，是纹理——因为在很长一段时间里，它都是 GPU 上的头号内存大户。

🔍 专家解析

这里给出的其实是“虚拟化复兴”的宏观成因，可以直接抽象成一条供需曲线：显存供给随硬件世代线性缓慢爬升（主机世代内甚至是常量，PS5/Xbox Series 约 10–13GB 可用），而需求随特性数量近似相乘式增长——距离场要一份、Lumen 表面缓存要一份、光线追踪的加速结构与 BLAS 要一份、虚拟阴影贴图的页缓存要一份、再加上纹理与几何体本体。当需求增速长期高于供给增速，唯一出路不是“买更多显存”，而是“让每个特性的驻留集与屏幕上实际可见的内容成正比”——这正是虚拟化的定义式回应。值得带走的一条横向观察：本讲列出的几个“抢显存者”里，距离场和 Lumen 表面缓存本身就是虚拟化或类虚拟化结构（距离场按组件稀疏生成并分 mip，Lumen 表面缓存是按需捕获到图集里的虚拟页），Nanite 与虚拟纹理是显式虚拟化，虚拟阴影贴图是虚拟化的阴影页。也就是说 UE5 的渲染架构演进方向可以一句话概括：把所有“按世界规模分配资源”的结构，改造成“按屏幕规模分配资源”。代价也要记下：虚拟化把内存压力转移成了 CPU 调度成本、反馈通道成本和更复杂的失效模式（页抖动、驻留不足、上载带宽），这些正是本讲后半段逐一展开的内容。

虚拟纹理比较麻烦的一点是：它不是引擎的默认开启特性。你必须手动启用——进到项目设置（Project Settings）里，勾上“启用虚拟纹理支持（Enable Virtual Texture Support）”，这些都打开了才能用。虚拟纹理大体有两种用法。基本原理是：虚拟纹理会把一张很大的纹理切成一个个独立的分块（tile），然后判断我们能看到哪些块。我这里准备了一个小可视化——谢谢——可以看到一小块一小块的 tile，然后我们说：好，这些才是 GPU 上真正可见的 tile。这就像是在“掐掉多余的 mip（nipping mips）”，对吧？如果只能看到右下角那一块，那我们就只把右下角那一块送上去。而这样做最大的显存收益之一是……

三个可带走的点。第一，“默认不开”不是技术不能，而是兼容性权衡：启用虚拟纹理要求材质里的纹理采样节点使用专门的虚拟采样器类型（Sampler Type: Virtual Color / Virtual Normal 等），这是编译期决定，改了就要全量重编译材质，并且旧的材质函数、插件、市场资产都可能不兼容；同时 DDC 与烘焙产物格式也会变。Epic 把它留成显式开关，等于把迁移成本交给了真正需要它的团队——所以“从第一天就规划虚拟纹理”是本讲反复出现的主题。第二，“nip mips”是引擎术语，指的是 mip 链上的稀疏驻留：传统纹理流送只能整张整级地驻留（mip0 常驻与否是二元决定），虚拟纹理可以把“mip0 的某 128×128 子矩形”单独驻留，粒度从“级”细化到“页”，这是它比传统流送省得多的根本原因，也是后面 Hillside 22GB→500MB 数字的前提。第三，tile（页）在 UE 的 SVT 里通常是 128×128 纹素加边框，页大小是所有权衡的支点：页越小稀疏性收益越高但页表与上载次数越多，页越大则反过来——这与 Nanite 的 128 三角形簇（cluster）、虚拟阴影贴图的页尺寸选择是同一类设计决策，建议把这几个数字放在一起记。

🔍 专家解析

这是全场含金量最高的一组数字，值得把每一项的含义和倍率拆清楚。压缩比是 22 GB : 500 MB ≈ 44 : 1，而且注意这不是压缩算法带来的（磁盘上那 22 GB 本来就是 BC 压缩后的体积），纯粹是“稀疏驻留”带来的：屏幕上真正需要的页才占显存。三项指标各司其职：required pool（100 MB）是传统纹理流送路径需要的 mip 驻留量——即那些没被虚拟化的纹理（UI、小图、非虚拟采样器引用的图）；total physical memory（423 MB）是虚拟纹理物理页池，即真正装着纹素的页集合；page table memory（48 MB）是页表本身，也就是“虚拟地址→物理页”的索引，它的体积与虚拟纹理总量、层数、页表层级相关而与可见内容无关，所以它是虚拟化的固定开销，也是“不要为小纹理上虚拟化”这条反向建议的来源。这个案例还有一个常被忽视的生产前提必须点明：Hillside 是从第一天就按全虚拟纹理设计的——材质里的采样器全是虚拟采样器类型，所以 required pool 才能被压到 100 MB。反过来，一个中途迁移的老项目里大量材质仍走传统流送，虚拟化收益会被显著稀释。对照 Nanite：二者都是“驻留集由屏幕覆盖决定”，但 Nanite 的页是 128 三角形簇、需求由逐簇的屏幕空间误差（screen-space error）判定，虚拟纹理的页是纹素矩形、需求由颜色反馈判定；两者的内存曲线都近似与“屏幕上该内容的像素占比”成正比，而不是与资产体积成正比——这是虚拟化家族共享的最核心性质。

“堆栈”是虚拟纹理反馈机制里最容易被误解的概念，值得彻底讲清。反馈通道的工作方式是：GPU 渲染主视图时，把“我采到了哪个虚拟纹理的哪一页、要哪一级 mip”写进一张小反馈缓冲；问题是这张缓冲是按屏幕像素组织的，要区分“采的是哪张虚拟纹理”，就必须为每种独立的 UV 映射（即每个堆栈）各写一份信息。所以堆栈数直接乘进反馈带宽、反馈分析 CPU 成本，以及页表的遍历成本——这正是他说的“每多一个堆栈就多一本书要看”。关键辨析：判断标准不是“用了几个纹理采样节点”，而是“有几条不同的 UV 变换链”。同一个 TexCoord×2 分出去接五个采样节点，仍然是一个堆栈；复制节点后只改其中一个的平铺倍率，就多出一个堆栈。由此得出可执行的生产守则：把平铺倍率统一化（同类资产共享一套 tiling），或者把不同的平铺需求改用世界空间三平面投影（WorldAligned 系列函数）在着色时计算而非新增 UV 链——不过要注意三平面采样本身有带宽成本，是另一种取舍。此处埋下的伏笔在后面兑现：堆栈越多，反馈通道越无法保证每帧覆盖到每张虚拟纹理，一旦叠加页驻留计时器，就会触发“页被疏汰→下一帧又请求→再上传”的抖动，表现为静态场景下 stat virtualtexturing 的 Map Requests 异常高。所以“没有硬性上限”这句话背后其实有一条可测量的红线：静态场景下 Map Requests 应趋近于零，不趋近零就说明堆栈/驻留配置出了问题。

🔍 专家解析

这两个问答各含一条容易记错的参数语义，值得单独钉住。“Convert to Virtual Texture 对话框里的数值”是尺寸阈值（size threshold），不是目标尺寸——它是一个过滤器：只有分辨率 ≥ 阈值的纹理才会被实际转换。这与前半段 Auto Virtual Texture Sizing（4K 以上自动虚拟化）是同一思想的手动版，也因此继承了同一条注意事项：把阈值设得过高（比如 4096）会让批量转换悄悄空转，你以为迁移完成了，实际上一张都没转——这种“静默无操作”比报错危险得多，所以批量迁移后必须抽查资产的 VT 标记与 stat streaming 的 required pool 变化来做验收。第二个问答的价值在于问答双方各自给出了一条真实的生产经验：提问方是做线性内容的团队，按关卡内存差异想按 map 配置池子；回答方指出池子是项目级配置，且 Auto Grow 每次增长都有重分配 hitch——所以“运行中动态调池子”是反模式，正确姿势是前期测量、固定配置、必要时用 device profile 分平台偏置。而 Matt 最后的反问“你省下内存要干什么”其实是全场方法论的点题：省内存不是 KPI，把省下的预算重新分配到更需要的地方（阴影距离、Lumen 质量、动态分辨率余量）才是；如果没有任何地方需要这笔内存，那过度调优本身就是浪费的工程时间。这个提问视角可以作为一个标准复盘问题写进性能优化 checklist 的第一行——先说目标，再谈数字。

🔍 专家解析

这最后一段反馈把两个最有生产价值的坑留到了全场末尾，值得作为收尾重点。第一个坑是离线烘焙路径吃不到流送的确定性：HLOD 生成与 World Partition 小地图导出都是“一次性把大范围内容烘进一张图”的操作，它们假设纹理已完整驻留；而虚拟纹理的驻留由反馈驱动、由屏幕可见性驱动，编辑器在烘焙时往往只加载了可见区域的页，于是烘出的 HLOD 贴图和小地图带着未就绪的降级 mip，产出一个永久模糊的资产——错误被“烘焙”进了静态数据，之后无论运行时池子多大都救不回来。这就是典型的“虚拟化失效模式叠加离线管线”问题：前者假设局部性，后者要求全集。规避手段是在生成前预热/强制驻留相关纹理（比如 r.Streaming.FullyLoadUsedTextures 一类强制全载手段、或先用相机扫一遍目标区域），并在产出物上做清晰度验收。第二个坑是全场技术含量最高的一句：RVT 的绘制通道没有反馈通道。反馈通道是虚拟纹理闭环的“需求探测”环节（前半段定义三构件之一），SVT 的采样依赖它来上报“我需要哪页哪级 mip”；但 RVT 的绘制发生在“生成页”的渲染过程中，此时不可能再为其中的 SVT 采样建立反馈回路——引擎不知道该把哪些 SVT 页调进来，于是要么采样到未驻留的最低 mip（糊），要么拿到无效数据（粉/黑）。结论因此是硬性的、不可协商的：参与 RVT 绘制的材质里不能用虚拟纹理采样。这与问答环节前面那句“minimap/HLOD 发糊”是同一个原理的两次表现。把两者合并成一条可带走的规则：任何“非屏幕驱动的纹理消费路径”——离线烘焙、RVT 页生成、小地图导出、贴花烘焙、HLOD——都不应使用依赖反馈通道的虚拟纹理输入；这些路径的材质要用普通流送纹理单独维护。检查时机放在地形材质评审阶段最便宜，因为地形材质恰恰是最容易混用 RVT 输出与大范围 SVT 采样的地方。
